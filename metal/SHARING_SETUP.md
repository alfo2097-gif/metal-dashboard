# 금속 대시보드 공유 입력 설정

**로그인 없이 같은 공개 링크에서 누구나 읽고 편집·저장합니다. 외부 방문자도 동일한 권한으로 내용을 바꿀 수 있습니다.** 별도 편집 URL이나 계정 승인은 없습니다. 링크/공개키를 알게 된 사람이 API를 직접 호출하는 것도 가능합니다. 익명 훼손, 반복 저장, 트래픽·비용 악용의 위험을 수용하는 운영 방식입니다. CAS는 동시 덮어쓰기 충돌만 줄이고 악의적 변경은 막지 못합니다. 백업·복원도 재훼손이나 남용을 막는 보안 장치가 아닙니다.

초안, 이메일, UUID, 비밀번호, 계정 정보, 내부 기밀은 공유 데이터에 넣지 마세요. 필드 제한은 개인정보 자동 탐지가 아니므로 사유·뉴스·시트명 안에 직접 적은 민감한 내용까지 차단하지 못합니다.

## 사용하는 순서

1. 최초 연결 뒤 현재 10/23·10/30 자료를 확인하고 상단 **저장**을 누릅니다. 최초 저장 역시 공개 게시입니다.
2. 누구나 주요 Metal 시세 아래 **변동 사유 칸에 직접 붙여넣은 뒤 상단 저장**을 누릅니다. 확정된 사유는 **수정**으로 풀고 편집합니다. 붙여넣기는 줄바꿈을 유지한 일반 텍스트로 처리합니다. 별도 금주 가안 편집 영역은 없으며 기존 개인 가안 데이터는 백업에 보존합니다.
3. 다른 화면은 Realtime 알림으로 갱신하고, 연결이 끊긴 경우 활성 화면에서 30초마다 확인합니다. 타이핑 중인 화면은 덮어쓰지 않습니다. 상단은 저장 버튼만 표시하고 필요한 상태/오류 안내를 곁들입니다.
4. **최신 시세**는 최신 수집 주차, 날짜 버튼은 해당 작성일의 대상 주차를 표시합니다. 사유의 실제 작성일/대상 주차는 별도로 표시됩니다. 더보기·백업·작성일 추가 버튼은 간소화 요청에 따라 상단에서 제거했습니다. 기존 데이터와 내부 유지보수 함수는 삭제하지 않았습니다.
5. 충돌 안내가 나오면 **저장**을 누릅니다. 확인 후 내 작업본이 JSON 백업으로 다운로드되고 최신 공유본을 불러옵니다. 백업의 필요한 문장/숫자만 최신 본문에 다시 옮겨 저장하세요. 다른 버전의 전체 덮어쓰기는 하지 않습니다.

## 1. Supabase 준비

1. Supabase에서 프로젝트를 만들고 프로젝트 URL과 **Publishable key (`sb_publishable_…`)**를 확인합니다.
2. SQL Editor에서 같은 폴더의 `shared-schema.sql` 전체를 관리자 계정으로 실행합니다. 외부 DB 자동 실행은 하지 않습니다. 재실행해도 기존 스냅샷은 삭제하지 않습니다. 기존에 같은 이름의 다른 구조를 만든 경우 먼저 별도 검토하세요. 이전 승인 모델의 편집자 테이블이 있으면 데이터는 남기되 공개 접근을 차단하고 저장에서 사용하지 않습니다.
3. Realtime에서 `public.metal_shared_state`의 Postgres Changes가 활성화됐는지 확인합니다. SQL은 `supabase_realtime` publication이 존재하면 이 테이블을 중복 없이 추가합니다. publication이 없으면 안내 NOTICE를 표시하며, 이때는 폴링으로 동작하고 Realtime 준비 후 SQL을 다시 실행할 수 있습니다.

Auth 가입·계정 생성·로그인·UUID 승인 설정은 필요하지 않습니다. Supabase의 익명 **Auth 로그인**을 켜는 것도 필요 없습니다. 비로그인 요청의 `anon` 역할로 읽고 저장합니다. 관리자 소유의 `SECURITY DEFINER` 저장 함수가 데이터 형식과 revision을 검사합니다. 클라이언트에는 SELECT와 해당 RPC 실행만 허용하고 직접 INSERT/UPDATE/DELETE는 금지합니다. 관리자 SQL Editor는 이 클라이언트 제한의 대상이 아닙니다.

## 2. 클라이언트 설정과 저장 규약

클라이언트 파일명은 `shared-config.js`, `shared-store.js`입니다. `shared-config.js`의 설정은 다음 형식만 사용합니다. 이 안내와 SQL만으로 기존 HTML에 클라이언트가 자동 연결되지는 않으므로, 해당 파일과 HTML 연동이 준비됐는지 배포 전에 확인하세요.

```js
window.METAL_SHARED_CONFIG = {
  url: 'https://프로젝트참조.supabase.co',
  publishableKey: 'sb_publishable_프로젝트공개키'
};
```

공개 설정은 URL과 Publishable key뿐입니다. **`sb_secret_…`, service-role key, DB 접속 비밀번호, 로그인 비밀번호, 액세스 토큰은 배포 파일에 넣지 않습니다.** 공개키 자체는 비밀이 아니며 편집 비밀번호가 아닙니다. DB 권한/RLS/RPC는 저장 경로와 데이터 형식을 제한할 뿐 방문자를 구분하거나 악성 편집을 막지 않습니다. 설정 파일은 `shared-store.js`보다 먼저 로드합니다.

- 읽기: `public.metal_shared_state`에서 `id='main'` 조회. 최초에는 0행이며 아직 게시하지 않은 상태입니다.
- 저장: `metal_save({p_expected_revision: 읽은 revision, p_payload: 전체 공유 데이터})` RPC만 사용합니다. 초기 0행 상태의 예상 revision은 **0**, 최초 저장 결과는 **1**입니다. 이후 매번 1씩 증가합니다. 결과는 저장된 행을 담은 배열(SETOF)입니다.
- `40001`: 다른 사용자가 먼저 저장했습니다. 최신 내용을 다시 읽고 본인 변경과 병합한 뒤 확인받아 저장합니다. 같은 내용을 최신 revision으로 자동 덮어쓰기 하지 않습니다.
- `42501`: 권한 설정 또는 잘못된 직접 쓰기 경로 문제이며 로그인으로 해결하는 모델이 아닙니다. `22023`: 데이터 검증 실패입니다.
- `locks`는 업무상 확정 표시일 뿐입니다. 누구나 RPC로 바꿀 수 있으며 변경 불가 보장이 아닙니다.

### 실시간 반영

`shared-store.js`는 `postgres_changes`의 `event: '*'`, `schema: 'public'`, `table: 'metal_shared_state'`, `filter: 'id=eq.main'`을 구독하고 알림을 받으면 최신 행을 SELECT합니다. 로그인 없이 동일한 Publishable key를 사용합니다. INSERT/UPDATE 알림은 저장 트랜잭션이 커밋된 후 전달되며, 네트워크와 서비스 상황에 따라 지연되는 **준실시간** 방식입니다.

첫 로드, 재연결 및 주기적 폴링에서도 SELECT하여 구독 단절/누락을 복구합니다. Realtime을 사용할 수 없어도 폴링으로 다른 브라우저의 변경을 가져와야 합니다. 편집 중인 로컬 미저장 내용을 원격 알림으로 조용히 덮어쓰지 말고 충돌 안내와 병합 절차를 유지합니다.

### 공개 payload 형식

아래 여섯 최상위 키가 모두 필수이며 추가 키는 허용하지 않습니다. `revision`, `updated_at`은 payload 밖의 서버 관리 열입니다.

```json
{
  "schema": 1,
  "reports": {
    "2026-10-30": {
      "f": "2026-10-30", "sheet": "주간보고",
      "s": "은 사유", "a": "알루미늄 사유", "c": "동 사유", "n": "비고"
    }
  },
  "locks": {"2026-10-30": true},
  "silver": {"2026-10-30": 100},
  "news": [{"m": "Silver", "t": "제목", "u": "https://example.com/", "s": "출처", "d": "2026-10-30 09:30"}],
  "latest": "2026-10-30"
}
```

- 빈 최초 값: `{"schema":1,"reports":{},"locks":{},"silver":{},"news":[],"latest":""}`.
- 날짜 키는 실제 존재하는 `YYYY-MM-DD`입니다. 보고서의 `f`는 금요일이며 해당 보고서 날짜 이하, 최대 7일 전까지입니다. 보고서의 6개 키는 모두 문자열이고 추가 키는 불가합니다. `s/a/c/n` 각각 최대 20,000자입니다.
- `locks` 값은 boolean이며 모든 키에 보고서가 있어야 합니다. `latest`는 빈 문자열 또는 존재하는 보고서 날짜입니다.
- `silver`는 날짜별 양수 JSON 숫자이며 1,000,000 이하입니다.
- 뉴스의 `m/t/u/s/d`는 모두 필수 문자열이며 추가 키 불가. `m`은 `Silver`, `Aluminium`, `Copper` 중 하나입니다. `d`는 실제 날짜 또는 `YYYY-MM-DD HH:mm`(00:00~23:59)입니다.
- `u`는 빈 문자열 또는 HTTP(S) URL만 허용합니다. 호스트가 필요하고 공백·제어문자·역슬래시 및 사용자정보를 담은 URL은 거부합니다. 국제 도메인은 ASCII/Punycode를 사용하세요. 클라이언트도 문자열을 HTML로 삽입하지 않고 안전하게 렌더링해야 합니다.
- 최대 크기: 정규화된 JSONB 텍스트의 UTF-8 크기 **2 MiB(2,097,152바이트)**, 보고서 2,000개, 은 값 10,000개, 뉴스 500개. 원본 JSON의 들여쓰기 크기와 DB 측정 크기는 다를 수 있습니다.
- `drafts`, 사용자/계정 식별 필드 등은 허용하지 않습니다. 로컬 가안이나 기존 백업 전체를 그대로 공유 스냅샷에 업로드하지 않습니다.

## 3. 기존 Pages에 수동 배포

1. 기존 Pages 호스팅의 현재 수동 업로드 절차를 이용합니다. Git 저장소나 Git 명령은 전제하지 않습니다.
2. HTML, 연동된 `shared-config.js`/`shared-store.js`, 공개용 데이터와 필요한 정적 파일을 준비합니다. SQL 파일과 운영 메모는 웹 배포물에 넣을 필요가 없습니다.
3. **기존 공개 `draft.js`는 배포 묶음에서 빼는 것만으로 끝내지 말고, 호스팅에 남아 있는 파일도 삭제**합니다. HTML의 `<script src="draft.js">` 참조도 제거한 버전을 배포하세요. 비공개 초안은 로컬에서만 보관합니다. 이 안내는 기존 파일을 자동 삭제하지 않습니다.
4. 예전 배포 URL/미리보기, CDN 캐시와 브라우저 캐시도 확인하고 가능한 범위에서 삭제·무효화합니다. **이미 공개된 초안의 다운로드·캐시·복사본까지 회수되지는 않습니다. 삭제는 소급적인 비공개 전환이 아닙니다.** 민감한 정보가 있었으면 별도로 노출 대응하세요.
5. 로그인하지 않은 서로 다른 두 브라우저에서 읽기·저장 성공과 반대쪽 화면의 실시간 반영을 확인합니다. WebSocket이 끊겨도 폴링으로 갱신되는지, 직접 테이블 쓰기 거부·오래된 revision 충돌·잘못된 payload 거부도 검사합니다. 구체적인 SQL 테스트 순서는 스키마 파일 끝 주석에 있습니다. 테스트는 별도 프로젝트 또는 ROLLBACK으로 수행하세요.
6. 공개 전 별도 장소에 정상 스냅샷을 백업하고 복원 절차를 시험하세요. 복원도 최신 revision을 읽고 CAS 저장해야 합니다. 남용 시 관리자가 `metal_save` 실행 권한을 회수하거나 서비스를 중지할 수 있지만, 공개 쓰기가 켜져 있는 동안 백업만으로 악용을 막을 수는 없습니다.

**공유 입력과 자동 수집 데이터는 별개입니다.** 보고서 사유·확정 표시·수동 은 값·직접 추가 뉴스·최신 보고서 선택은 Supabase 스냅샷 저장으로 다른 브라우저에 공유됩니다(Realtime 알림에 따른 재조회 및 폴링으로 반영). 자동 수집 시세·재고·기본 뉴스 등 기존 정적 JS 데이터의 갱신은 여전히 수집 작업 후 Pages에 파일을 다시 배포해야 합니다. Supabase 저장이 자동 수집 실행이나 Pages 배포를 대신하지 않습니다.
